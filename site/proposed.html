02 / Proposed design · Three priorities

Preserve work, contain retries, make repetition safe

One durable delivery intent owns each accepted event's next action. Processing and delivery retry independently; an ambiguous endpoint outcome reuses the same identity and payload. Scope follows the three ranked priorities.

P1 · Make ownership survive each handoff

Ingestion confirms acceptance only after durable append. Processing looks up the tenant/event ID before doing work. It atomically commits the immutable enriched result and a unique delivery intent in waiting_index. On replay, it resumes the saved result instead of enriching it again.

The existing index write remains a delivery prerequisite. After an idempotent index write is acknowledged, processing conditionally marks the intent ready and then acknowledges the input. A crash before readiness leaves input replayable; a crash after readiness finds the existing intent. A duplicate index write is safe by stable event identity. The index and event store still do not share a transaction.

Before the first result commit, processing failures may repeat enrichment. Defer input retries durably, bound their age/attempts, and persist a needs-attention record before acknowledging an exhausted or permanently failed event. Reconciliation identifies stale waiting_index work and resumes indexing from the saved payload.

Persistence assumption: the event store supports atomic result/intent writes, uniqueness by tenant/event and destination, and conditional state changes. The input buffer supports durable replay and bounded redelivery. Retention must cover the recovery window. These capabilities are implementation prerequisites.

P2 · Retry delivery without repeating processing

A dispatcher polls due intents directly from the store and claims them with a lease and attempt token. This store is the delivery work queue; a separate relay and delivery broker are unnecessary for this scope. Due-time lookup, lease contention and store capacity require peak-load validation.

Only ready or due-retry work can be claimed. Enforce per-tenant/endpoint limits, request deadlines, delayed backoff with jitter, and maximum attempts and age. Retry transient or ambiguous outcomes; permanent failures and exhausted budgets become durable needs_attention work with an owner. Circuit-open work is deferred without an outbound attempt, while its age limit still applies.

Commit the attempt outcome, next due time or terminal state, and lease release together under the current token. If that write fails, leave the claim recoverable. Expired in-flight claims are treated as potentially delivered and rescheduled under the same key and budget. No failed delivery is republished to the processing bus.

P3 · Protect ambiguous outcomes

Snapshot the destination, delivery key and enriched payload in the intent. Scope the key by tenant, event and destination; reject conflicting payload reuse. Each claim has a new attempt token, but every external retry retains the same delivery key. Conditional updates prevent expired workers or late failures from regressing an accepted state; leases alone cannot stop overlapping external requests.

The recipient must persist the deduplication key atomically with its side effect, return the previous acceptance on duplicates, and retain keys through the retry and permitted replay window. A receiver that cannot do this may repeat effects. Endpoint acceptance does not establish completion of the customer's internal workflow.

The existing dashboard/API reads authoritative per-delivery status from the intent record: pending, in flight, retry due with an unknown outcome where applicable, endpoint accepted, or needs attention. Include last attempt, next action and state version. This is the minimum feedback needed for P1 recovery and P3 correctness; general event-search freshness and reporting remain outside this change.

Scope and residual risks

Search outages can still delay readiness; the durable input and saved result make that delay recoverable, not harmless. Cross-view consistency, global delivery ordering, platform-wide admission redesign and multi-region recovery are deferred to 04 Future scope. Existing gateway authentication, tenant scoping and rate limits remain required.

The selected mechanisms apply durable delivery, atomic outgoing intent, idempotent receiver, retry, circuit breaker and bulkhead patterns. Validation and rollout gates remain on 01.2 Failure priorities; the exact runtime flow is on 03 Delivery sequence.
