1.2 / Architecture Patterns

Architecture Patterns for the mapped challenges

These established patterns provide a vocabulary for evaluating the current failure modes. Each is a candidate with a specific purpose and tradeoff; selection follows the completed current-state analysis.

Challenge links return to the relevant assumption or behavior in Current Flow. Pattern links point to the original catalog or authoritative architecture guidance; the applications below are specific to this case.

Current challenge, candidate pattern, fit, and limits
Current challengeEstablished patternWhy it fitsLimits and tradeoffs
Acknowledged work can lose its durable owner Guaranteed Delivery Persistent messages and acknowledgment boundaries keep work recoverable across a crash until a durable receiver takes responsibility. Requires persistent storage and correct acknowledgment timing at each handoff. It does not guarantee eventual acceptance by an unavailable customer endpoint or completion inside that customer's system.
A result is stored but its delivery handoff is lost Transactional Outbox Commits the result and an outgoing delivery intent in one local transaction. A relay can resume publication after a crash, closing the gap between persistence and messaging. Needs a shared transaction boundary for state and intent, plus relay operations. Publication can duplicate messages. It does not atomically commit the search index or the customer's side effect.
Retries repeat processing or customer side effects Idempotent Receiver Uses deduplication or operations with the same effect on repetition, making repeated receipt safe after ambiguous failures. Needs a stable identity and a defined deduplication scope and retention period. Platform-side deduplication cannot enforce idempotency inside a customer endpoint the platform does not control.
Transient faults and persistent outages trigger repeated work Retry and Circuit Breaker Retry handles recoverable failures with controlled spacing and limits. A circuit breaker temporarily stops calls to a persistently failing dependency, allowing recovery. Requires failure classification, deadlines, and coordinated retry budgets. Layered retries multiply load. Circuit-open work still needs a durable owner; neither pattern removes duplicate side effects.
One tenant or endpoint consumes shared capacity Bulkhead Separates resource pools or concurrency budgets so slow endpoints and high-volume tenants cannot consume every delivery slot. Isolation can leave capacity unused and adds scheduling complexity. Shared brokers, storage, and enrichment remain possible bottlenecks; isolation must cover the actual constrained resources.
Undeliverable events can circulate indefinitely Dead Letter Channel Separates work that cannot be delivered from normal traffic, preserving it for diagnosis and controlled recovery. A holding area does not fix the failure. It needs an owner, retention policy, alerts, and safe replay rules; customers still need a visible terminal or needs-attention status.
Search writes gate delivery; read views diverge CQRS and materialized views Separates state-changing operations from read projections. It provides a model for a search/dashboard view that updates independently of delivery-critical state. Introduces projection lag, replay/rebuild operations, and ordering concerns. It does not automatically repair lost updates or prevent stale status from overwriting newer state. CQRS does not require event sourcing.
Event progress and delivery attempts are hard to reconstruct Message History Records the stages a message traverses. Associated event and attempt identities help explain where processing stopped and which attempts produced customer-visible status. History has storage, retention, and privacy costs. An audit trail is evidence, not durable work ownership, guaranteed status convergence, or proof of customer processing.

Use the current-state assumptions to distinguish established behavior from assumed failure modes before choosing a pattern.
