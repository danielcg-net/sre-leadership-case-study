03 / Delivery sequence · Three priorities

A lost response must not lose work or change retry identity

This sequence follows one event from durable processing ownership to a customer acceptance whose response is lost. The dispatcher retries the saved intent directly; the cooperating receiver recognizes the delivery key and does not repeat the effect.

Recovery at the boundaries

  1. P1 · Before input acknowledgment

    Reuse a committed result on redelivery. If indexing fails, keep input replayable and defer with a budget. Ready or terminal intents do not repeat processing; exhausted processing is durably retained for attention before acknowledgment. Index acceptance is a readiness gate, not a transaction with the event store.

  2. P1 + P2 · During a delivery claim

    A crash or failed outcome write leaves a recoverable lease. Expiry does not prove the customer did nothing; reschedule with the same key, a new attempt token and the remaining retry budget. Budget exhaustion retains needs-attention work.

  3. P3 · After customer acceptance

    A lost response triggers an ambiguous retry. Recipient deduplication must cover the side effect and key in one transaction. Once acceptance is stored, late attempt tokens cannot regress status; already-sent requests can still arrive, so recipient deduplication remains necessary.

  4. P1 + P3 · Controlled recovery

    Replay saved work with the original key and payload within the agreed deduplication window. Changing the destination or payload, or replaying after key expiry, requires an explicit recovery decision because it can repeat a customer action.
