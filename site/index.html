1.1 / Current Flow

Failures return to the full processing path

Processing acknowledges on receipt. Every failed delivery returns to the event bus and repeats processing, including enrichment. Slow enrichment and delivery retries can therefore compound the backlog.

Assumptions and architectural impact

  1. Enrichment gates processing

    Assumption: processing uses synchronous request-response enrichment and needs the result before writing or forwarding the event. This is a completion dependency, not a requirement to block a worker thread.

    Impact: slow enrichment increases in-flight work and delays every later stage. Finite concurrency fills up, and retries compete with new events for the same capacity.

  2. Both persistence writes gate delivery

    Assumption: processing waits for successful datastore and search-index write acknowledgments before handing the event to delivery. The writes may run in parallel, but do not share an atomic transaction. An index write acknowledgment need not mean the event is already searchable.

    Impact: either write can delay delivery after enrichment completes. One write can succeed while the other fails, leaving inconsistent views and partial work to recover. Reprocessing repeats enrichment and writes, adding load to already degraded dependencies.

  3. Dashboard/API reads are independent of delivery

    Assumption: the dashboard and API read stored event and delivery status on demand; processing does not wait for a UI refresh or API read. Some delivery-status reporting exists, as the scenario requires. We assume outcome updates are separate from attempts and retry publication, with no guaranteed atomic commit across them.

    Impact: dashboard/API serving is not another delivery gate. An event can appear before delivery succeeds; index refresh delays or failed status writes can leave its displayed state stale. Shared storage load can still degrade reads. Visibility is not proof of delivery.

  4. A failed attempt can repeat a successful side effect

    Assumption: timeouts and lost responses count as failed attempts, even if the customer endpoint accepted the event. Neither repeated processing nor recipient handling is guaranteed to be idempotent.

    Impact: republishing can cause duplicate deliveries and customer side effects. Repeated writes may create duplicate records without a stable key or unique constraint, and repeated enrichment may change the payload. A definite rejection need not duplicate a successful delivery; an ambiguous outcome can.

  5. Persisted events can become stranded

    Assumption: acknowledgment on receipt ends event-bus redelivery. No durable delivery intent or reconciliation process recovers a lost handoff or retry publication.

    Impact: a crash before persistence can lose unfinished work. A crash after persistence but before handoff, or a failed retry publication, can leave a dashboard-visible event with no remaining delivery work. A downstream outage alone causes delay while retries survive; permanent stranding requires this recovery gap. Stored events therefore need durable delivery ownership and reconciliation.

  6. Views can diverge and status updates can arrive out of order

    Assumption: event data, search results, and delivery status become visible independently. There is no atomic snapshot across them; updates may arrive late, more than once, or out of order. Version checks and status-ordering guarantees are unspecified.

    Impact: the API and dashboard can show different versions of the same event. Without ordering protection, an older failure can overwrite a newer success. Synchronous write acknowledgment does not guarantee immediate visibility across all views. Temporary lag is eventual consistency only if updates eventually converge; a lost update without replay or reconciliation can leave permanent divergence. No maximum freshness lag is specified.

Customer endpoint failure boundary

The customer owns the receiving infrastructure. The platform owns delivery attempts, recovery, and truthful status. The current retry mechanism republishes failed events to the event bus; durable retry scheduling, limits, and status-update guarantees are not specified.

  1. Endpoint acceptance is the observable boundary

    Assumption: the platform observes an endpoint response or a timeout, with no separate receipt confirming completion inside the customer's system.

    Impact: a success response establishes acceptance under the webhook contract, not completion of customer processing. A lost response leaves acceptance unknown. Retrying may duplicate a side effect; stopping may leave the event undelivered.

  2. External failures feed back into shared processing

    Current behavior: failed attempts repeat enrichment and persistence through the event bus. Retry pacing, maximum age, terminal failure handling, and per-endpoint isolation are unspecified.

    Impact: an unavailable or slow endpoint can amplify platform work. Without effective limits, its retries can delay healthy tenants. Repeated rejection needs a visible recovery state and an assigned owner; an endless retry loop is not recovery.

  3. Retry publication is not delivery-status feedback

    Assumption: delivery attempts to write outcomes separately to the shared store. A retry message alone does not reliably update customer-visible status, and no reconciliation repairs a lost status update.

    Impact: a retry can be pending while the dashboard shows an old failure, or the endpoint can accept the event while the dashboard still shows pending. If the status write and retry publication both fail, there may be neither visible failure nor remaining work. Delivery must retain durable ownership until the outcome and next action are recoverable.

Current-state gap: no durable link is specified between the attempt outcome, its next action, and customer-visible status. Retry publication alone does not establish that these agree.
