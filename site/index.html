SRE leadership case study / Architecture

Reliable webhook delivery

Preserve accepted events. Contain downstream failures. Make delivery outcomes observable.

Current flowProposed designDelivery sequence

Conceptual design exercise. The current flow reflects the scenario; changes below are proposals, not deployed or measured results. No infrastructure provider is assumed.

01 / Current flow

Failures return to the full processing path

Processing acknowledges on receipt. Every failed delivery returns to the event bus and repeats processing, including enrichment. Slow enrichment and delivery retries can therefore compound the backlog.

Open question: does acknowledgment on receipt leave any durable owner of unfinished work? Confirm the actual recovery contract before concluding that a crash loses events.

02 / Proposed design

Separate durable processing from delivery retries

Commit the enriched result and a delivery intent together before acknowledging processing. Deliver from durable work; retry the stored payload without re-running enrichment. Keep search indexing off the delivery-critical path.

  • Durability: accept ingestion only after durable append. Atomic result/outbox persistence is a required capability to validate.
  • Containment: bound enrichment calls, retry attempts and age, and per-tenant/endpoint concurrency. Circuit-open work remains pending with delayed retry; enrichment is not silently skipped.
  • Capacity: buffering buys finite time. Monitor oldest-event age and storage headroom; use explicit admission control before capacity is exhausted.
  • Tradeoff: extra queues and relay operations add complexity. Search may lag; expose freshness and pending delivery states rather than implying completion.

03 / Proposed delivery sequence

At-least-once delivery needs explicit duplicate handling

The retry reuses the event ID and enriched payload. A lost response or a worker crash can repeat a delivery even when the endpoint already accepted it. Recipient deduplication is part of the integration contract.

Recovery contract: processing is idempotent by tenant and event ID. Work leases expire after crashes. Rescheduling is durable before releasing the current claim; already-recorded success suppresses further attempts. Permanent failures and exhausted retries enter controlled recovery, not an endless loop. Delivery order is not guaranteed by this proposal.
